# 💻 Developer & Code Contributor Guide

Thank you for wanting to contribute code, UI design, performance optimizations, or script fixes to **Tool Shed (Tiny-island)**! This document provides everything you need to know about setting up your development environment, codebase architecture, testing pipelines, and submitting clean Pull Requests.

---

## 🛠️ Prerequisites

Before you start, make sure you have the following installed on your system:

- **Node.js**: `v20.0.0` or higher
- **npm**: `v10.0.0` or higher
- **Git**: Installed and configured with your name and email

---

## 🚀 Environment Setup

1. **Fork and clone the repository**:
   ```bash
   git clone https://github.com/YOUR-USERNAME/tiny-island.git
   cd tiny-island
   ```

2. **Install project dependencies**:
   ```bash
   npm install
   ```

3. **Start the development server**:
   ```bash
   npm run dev
   ```
   Open [http://localhost:3000](http://localhost:3000) in your browser. Next.js supports Fast Refresh, so any changes you save in `app/` or `components/` will update live.

## 🏗️ Project Architecture Overview

Here is a breakdown of the core directories and how the application works:

```
tiny-island/
├── app/                      # Next.js App Router
│   ├── layout.tsx            # Global HTML layout & meta tags
│   ├── page.tsx              # Homepage (renders ToolGrid & hero)
│   ├── pegboard/             # Pegboard view route
│   ├── contributors/         # Author pages route
│   └── globals.css           # Global design tokens & CSS styling
├── components/               # React UI Components
│   ├── ToolCard.tsx          # Card view for individual tools/games
│   ├── ToolGrid.tsx          # Filterable & searchable grid component
│   └── CategoryFilter.tsx    # Category/Tag filter UI
├── data/
│   └── tools.json            # Synchronized database (DO NOT edit manually)
├── scripts/                  # Node.js Automation Scripts
│   ├── validate-submission.mjs  # Validates GitHub issue repo URLs
│   └── sync-tools.mjs           # Fetches approved issues & builds tools.json
├── .github/                  # GitHub Actions & Templates
│   ├── ISSUE_TEMPLATE/       # Issue forms (tool submission, bug report, etc.)
│   └── workflows/            # CI/CD Workflows (validation & Pages deployment)
└── docs/                     # Contributor Documentation
```

## 🔄 Testing Scripts Locally

The site relies on static JSON data generated by GitHub Issues. You can test the sync and validation scripts locally on your machine:

### 1. Testing `sync-tools.mjs`
To run the sync script locally against the repository:

1. Create a GitHub **Personal Access Token (classic)** with `public_repo` scope at [GitHub Token Settings](https://github.com/settings/tokens).
2. Execute the script in your terminal:
   ```bash
   PERSONAL_ACCESS_TOKEN="your_personal_access_token" \
   GITHUB_REPOSITORY="Amanmeena0/tiny-island" \
   node scripts/sync-tools.mjs
   ```
3. Inspect `data/tools.json` to verify that tools were fetched, stars were calculated, and the JSON output is properly formatted.

### 2. Testing Static Production Export
To verify that Next.js successfully compiles and exports static HTML/CSS assets without errors:

```bash
npm run build
```
The compiled output will be generated inside the `out/` directory.

## 🎨 Code Style & Quality Guidelines

- **TypeScript**: Always write TypeScript with explicit interfaces or types for new components.
- **Styling**: We use Tailwind CSS v4 and custom design tokens in `app/globals.css`. Ensure new components match the aesthetic of Tool Shed (dark theme, crisp borders, glassmorphism accents).
- **Linting**: Run ESLint before committing your code:
  ```bash
  npm run lint
  ```
- **No Manual Mutations to `data/tools.json`**: Do not commit manually edited versions of `data/tools.json` unless fixing a schema bug in `scripts/sync-tools.mjs`.

## 📥 Submitting Your Pull Request

1. **Branch Naming**: Use a clear branch prefix:
   - `feature/add-dark-mode-toggle`
   - `fix/sync-script-rate-limit`
   - `docs/update-readme`
2. **Commit Messages**: Write meaningful commit messages (e.g. `feat: add tag filtering to pegboard`).
3. **PR Description**: Reference any related open issue numbers (e.g. `Fixes #12`).
4. **Verification**: Confirm `npm run build` succeeds before creating your PR.

Thank you for helping build Tool Shed! 🚀
